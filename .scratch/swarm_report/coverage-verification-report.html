Verification & Coverage in Phronesis

How coverage evidence, property ontologies, verification artifacts, and governance hooks interact — and what that machinery says about the code it governs.
feat/coverage-evidence · phr-mcp 0.35.0 · HEAD 1670052 · Sep 2026

What this system answers

One question sits under everything in this report: which tests exercise the code I changed, and where is the evidence missing? Phronesis answers it with three cooperating surfaces. phr-mcp coverage select is the host query — the union of dynamic hits from the evidence store and static graph reach, labeled by evidence kind. Rules 5.1 and 5.2 fire at hook time, logging the relevant-test join and warning on evidence gaps. Rule 5.3 warns when the store is stale against HEAD, so freshness is never a manual check. The property ontology layers intent on top of all of it: a property is a claimed behavior with a promotion lifecycle, and a formal proof is one kind of evidence among several — never a status change by itself.

Architecture — intent, evidence, consequences

Three kinds of state meet at one join point. Intent is what humans curate: properties.json (version-controlled, reviewed in PRs) and rules.json. Evidence is what the machinery derives: coverage hits from real test runs, verifier results, graph edges — durable but gitignored, rebuildable, never hand-edited. Consequences are what anyone sees: the log, warn, or block a hook emits at fire time. The RETE network is rebuilt fresh on every hook fire and joins all three. Nothing is cached between fires, so the verdict at 3am is computed from exactly the state on disk at 3am.

Property ontology

Properties are the layer that turns "this function has tests" into "this behavior is supposed to hold, and here is what would count as proof." The design split is deliberate: intent is version-controlled, evidence is derived. The record says what should be true; the sidecar says what has actually been shown, by which verifier, at which revision. Rules join the two and never conflate them.

Promotion lifecycle

The discipline. Rules report eligibility, never promote. A runtime_observation-sourced property stays candidate — no rule treats it as accepted even with a passing verification result attached. With two or more corroborated_by entries the eligibility rule logs; nothing more. Status changes only via the recorded set_property_status MCP act, with a required reason that lands in the audit trail. This is "observed ≠ intended" given teeth.

Verification track

Ten verification conditions, zero errors. Three invariants over the coverage machinery itself: the identifier charset that gates imported records, the FNV-1a determinism that gives branch anchors their durability, and the line-ordering check that keeps the store well-formed. The honest limit is right there in the word mirror: these proofs bind the spec to a faithful reimplementation, not to the production functions. A refactor of the original could drift from its mirror and the proof would stay green. Full token-stream normalization is the follow-up that closes that gap.

The governance pipeline

Here is the pipeline end to end. Every Edit, Write, or Bash call fires a hook; the hook builds a fresh RETE network; three demand-gated producers assert facts — structural (graph edges), coverage (changed regions, hits, gaps), property (records, obligations, staleness) — and the rules that mention those relations do the joining. The demand gate is the quiet hero: if no loaded rule mentions a coverage relation, zero coverage facts are asserted, by construction. The footprint is bounded by what the rule set actually asks about, not by a policy that can be forgotten.

What an evidence gap looks like, live. A post-check over the fixture crate edit warned on fn:divides_negative_values, fn:divides_positive_values, and fn:rejects_zero_denominator — each "has neither dynamic test evidence nor formal proof evidence" — while fn:safe_divide, which has imported dynamic hits, was not warned. The rule distinguishes "no test executed this function" from "this function has evidence," and a property record with a passing result does not silence it (finding B4, now pinned by test).

Coverage — the real numbers

The tarpaulin chapter is worth one honest paragraph: tarpaulin cannot instrument on macOS, and its failure mode is silent — it writes a plausible 6.4 MB HTML report over 23,181 traces with zero coverage inside. A coverage tool that lies by rendering is worse than one that crashes, so tarpaulin is gone and the collector is cargo-llvm-cov. The numbers below are from one real instrumented workspace run (nightly, --branch): the machinery's own modules — the code this report is about — land at 77–96% lines, with select.rs (67.9%) the honest low point. After the collector was ported into Rust, 40 machinery tests ran in isolation under coverage and their 2,274 region-validated records were imported into the evidence store — so the gap rules and coverage select now run on real evidence, not the toy fixture. Those records were collected from an uncommitted working tree and stamped with the HEAD of the time, not with a revision that contains the code they measured (see the note below). The collector is self-validating: every emitted identity must be independently produced by region_map, so nothing it imports can drift from what hydration joins.

What's validated — and what isn't

The accounting, stated plainly. What is validated is validated by execution — real exports, real hook binaries, real Z3 runs, a golden trace through the real RETE network. What is not validated is written down rather than hidden, because a coverage system that overclaims its own coverage would be the funniest possible failure mode.

Not yet validated

  • Performance at scale — closed-world gap computation reads the whole store; untested at 100k hits
  • Write / rename / MultiEdit shapes — post-check's change model is whole-file-Edit-first
  • Producer-scoped replace — two llvm-cov runs with different filters are last-writer-win today
  • Demand-gate derivation closure — a rule joining a derived view needs the closure chased to base relations
  • Curated property records in PRs — the gitignore carve-out exists; real records are still the fixture's
  • The devcontainer tier — spec'd, not image-built
  • C6 at other (language, verifier) pairs — those adapters don't exist yet
  • Verus mirrors vs production code — the drift gap described above
