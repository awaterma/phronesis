# Predicate test-coverage and quality-warning expansion plan

**Date:** 2026-08-22
**Branch:** `feat/structural-rule-migration`
**Status:** Planning document — no source changes, no commits.

## Summary

This plan addresses two goals grounded in a full audit of the phronesis
predicate and graph-relation inventory:

1. **Per-predicate test-coverage gap analysis.** Every predicate in
   `SyntaxFacts::PREDICATES` (`crates/phronesis-mcp/src/syntax/facts.rs:171`)
   and every relation in `GRAPH_RELATIONS`
   (`crates/phronesis-mcp/src/graph/hydrate.rs:18`) was cross-referenced
   against the inline `#[cfg(test)] mod tests` blocks in each extractor file
   and against `crates/phronesis-mcp/tests/syntax_integration.rs`. The gaps
   are catalogued below using five test-class codes:

   | Code | Meaning |
   |------|---------|
   | **FV** | Formatting variants — whitespace, single vs multi-line, trailing commas |
   | **CS** | Comment / string-literal negatives — predicate must not fire inside comments or string literals |
   | **TN** | Test-code-scoping negatives — predicate must be suppressed or scoped inside `#[cfg(test)]` / `tests/` / `benches/` |
   | **MS** | Malformed / partial-source safety — extractor must not panic on truncated or syntactically broken input |
   | **MH** | Multi-hit in one function — predicate fires correctly when a function body contains multiple occurrences |

2. **Quality-warning expansion.** Three capability families were
   investigated. The brief's original framing of "orphaned config/IaC
   diagnostic families" turned out to be **outdated**: `init.rs` already
   ships `lua`, `cue`, `json`, `yaml`, and `helm3` packs, each with a
   rule over the diagnostic predicates. The genuinely orphaned predicates
   are `generated_without_consumer` and `consumed_without_producer` only
   (both further confirmed to be in `graph/audit.rs`'s
   `QUERY_ONLY_RELATIONS`, so the engine itself suppresses them from audit
   findings, not just non-adoption). The plan refocuses accordingly and
   proposes a new `no_test_coverage` derived fact plus a
   `warn-untested-public-function` starter-pack rule.

**Revision note (this pass):** Part 1's original per-predicate table was
generated by a model that did not actually read `SyntaxFacts::PREDICATES`
despite claiming to — every predicate name it listed for the Rust
extractors (`rust_unwrap_call`, `rust_clone_count`,

in `docs.rs` — see the new P0 backlog item. A handful of small citation

## Part 2 — Quality-warning expansion

### 2.1 Config/IaC diagnostic families — already built, need fixes

**Finding:** The brief claimed these predicates were orphaned, but
`init.rs` already ships dedicated packs for each:

| Pack | Rules | Predicates consumed |
|------|-------|---------------------|
| `lua` | `warn-lua-dynamic-code-load` | `lua_dynamic_code_load` |
| `cue` | `warn-cue-import-diagnostic` | `cue_import_diagnostic` |
| `json` | `warn-json-schema-unknown-dialect` | `json_schema_unknown_dialect` |
| `yaml` | `block-yaml-duplicate-key`, `block-yaml-invalid-alias` | `yaml_duplicate_key`, `yaml_undefined_alias` |
| `helm3` | `warn-helm3-dynamic-tpl`, `warn-helm3-cluster-lookup` | `helm3_dynamic_tpl`, `helm3_cluster_lookup` |

**Recommendation: BUILD (fixes only).** These packs are already shipped
but have two bugs that should be fixed before any new quality-warning
work:

1. **YAML rule ID-vs-action mismatch.** `block-yaml-duplicate-key` and
   `block-yaml-invalid-alias` have `block-` IDs but use `warn` actions.
   Either rename the rule IDs to `warn-yaml-*` or change the actions to
   `constraint_violation` (which blocks at pre-check). The IDs should
   match the severity.

2. **Lua rule missing `edited_file` join.** `warn-lua-dynamic-code-load`
   uses `file_extension_is("lua")` instead of joining on `edited_file`.
   Graph relations describe the whole repo, so without the `edited_file`
   join, the rule re-reports every `lua_dynamic_code_load` fact in the
   project on every edit to any `.lua` file — even edits to unrelated
   files. Fix: add an `edited_file` condition (matching the pattern used
   by all `structural` pack rules) so the rule only fires for the file
   actually being edited.

**False-positive risk assessment:**

- `lua_dynamic_code_load`: Legitimate in some embedded Lua / game engine
  contexts. The `warn` severity is appropriate — it flags without
  blocking. No scoping needed beyond the `edited_file` join fix.
- `cue_import_diagnostic`: CUE imports are always explicit; a diagnostic
  means a real problem. `warn` is correct.
- `json_schema_unknown_dialect`: A `$schema` URL the extractor does not
  recognize. Low false-positive risk — the extractor recognizes the
  common dialects. `warn` is correct.
- `yaml_duplicate_key` / `yaml_undefined_alias`: These are always errors
  in YAML. The `block-` IDs suggest the intent is to block, but the
  actions are `warn`. Recommend changing to `block` (constraint_violation
  action) since duplicate keys cause silent data loss.
- `helm3_dynamic_tpl` / `helm3_cluster_lookup`: Legitimate in some Helm
  chart patterns. `warn` is appropriate.

### 2.2 `generated_without_consumer` / `consumed_without_producer` — skip for now

**Finding:** These two derived predicates are computed in
`graph/derive.rs:372` (`configuration_lifecycle_gaps()`). The function
performs a set-difference: `generates` minus `consumes_data` yields
`generated_without_consumer`; the reverse yields
`consumed_without_producer`. Both are unary `[artifact]`, derived
(`d=true`). Their siblings `generated_artifact_diagnostic` and
`unconsumed_data_key` ARE wired in the `structural` pack
(`graph/data_contracts.rs`). Verified: both `generated_without_consumer`
and `consumed_without_producer` are also listed in
`graph/audit.rs`'s `QUERY_ONLY_RELATIONS` const alongside
`rhai_binding_diagnostic` (see §2.5) — the engine itself refuses to turn
them into audit findings today even if a project authored a rule over
them, which is stronger grounding for "skip" than mere non-adoption.

**Recommendation: SKIP (needs more infra).** These predicates are
genuinely orphaned — no starter pack rule consumes them. However,
building a rule over them requires the `generates` and `consumes_data`
base edges to be meaningfully populated, which depends on the
`structural` pack's data-contract extraction being adopted in real
projects. Until there is evidence that projects are asserting
`generates`/`consumes_data` edges, a rule over the derived gaps would
fire on empty sets (no false positives, but no true positives either).
Defer until the data-contracts feature has adoption signal.

### 2.3 Test-coverage signal — BUILD `no_test_coverage` derived fact + rule

**Finding:** `tested_by`, `test_reaches`, and `defines_test` are
correctly-derived call-graph relations in `graph/extract.rs`. The only
consumer is `warn-untested-risky-call` (`init.rs:2181`), which fires
when a production function calls a risky API AND has no direct test
(`no_direct_test`). There is no general "this public function has zero
test coverage" rule.

**Blocker:** The rule DSL (`rules_file.rs`) supports only `Leaf` and
`Or` in `WhenClause` — no `Not` variant. Boolean `false` in a leaf
clause is a presence marker (line 42-43), not negation. So a general
untested-function signal must be a **server-computed derived fact**,
like `no_direct_test` already is.

**Template:** `no_direct_test` (`graph/derive.rs:475`) is a closed-world
negation of `tested_by` over `defines_fn`, filtered to production files.
It is unary `[func]`, derived (`d=true`).

**Proposed derived fact: `no_test_coverage`**

- **Name:** `no_test_coverage`
- **Args:** `[func]` — unary, the function symbol
- **Derivation logic:** For each `defines_fn` fact where the file is a
  production file (not `tests/`, not `benches/`, not `#[cfg(test)]`
  gated — reuse `is_test_target()` from `facts.rs:157` for the file-path
  check, and the cfg-gate detection from `extract.rs` for the
  `#[cfg(test)]` check), check whether `test_reaches` (transitive) has
  any edge from a test function to this function. If no `test_reaches`
  edge exists, emit `no_test_coverage(func)`.
- **Difference from `no_direct_test`:** `no_direct_test` checks only
  direct `tested_by` edges. `no_test_coverage` checks transitive
  `test_reaches` edges, so a function that is indirectly tested (called
  by a tested function) is NOT flagged. This reduces false positives
  for helper functions that are exercised through their callers' tests.
- **Scope:** Public functions only? The brief asks whether to exclude
  trait impls of standard traits like `Display`/`Debug` where
  "untested" is often fine. Recommendation: **Phase 1** flags all
  production functions with no transitive test reach. **Phase 2** adds
  filtering:
  - Exclude `pub fn` whose signature is a trait impl of a standard
    trait (`Display`, `Debug`, `Clone`, `Default`, `PartialEq`, `Hash`,
    `Drop`, `Iterator`). These are often trivial and tested indirectly.
  - Exclude functions with `#[allow(dead_code)]` or
    `#[cfg(not(test))]` attributes (intentionally untested).
  - Exclude functions in `main.rs` (entry points are typically not
    unit-tested).

**Proposed starter-pack rule: `warn-untested-public-function`**

- **Pack:** Add to the `rust` pack (or a new `coverage` pack if
  separation is preferred).
- **Phase:** `post` (warn, not block — test coverage is a quality
  signal, not a hard gate).
- **Priority:** 5 (low — informational)
- **Conditions:**
  - `no_test_coverage(?func)` — the derived fact
  - `edited_file(?file)` — scope to the file being edited
  - `defines_fn(?file, ?func)` — join to the file
- **Action:** `constraint_violation` with message:
  `"Function {func} in {file} has no test coverage (no transitive test reach)"`
- **False-positive risk:** Moderate. Helper functions called only from
  `main()` or from other untested functions will be flagged. The
  Phase 2 filtering (standard trait impls, `main.rs`, `#[allow]`)
  addresses the most common false positives. The `post` severity
  ensures the rule warns without blocking.

### 2.4 Workspace/module-topology predicates — intentionally skip

**Predicates:** `build_member`, `includes_file`, `reexports`, `exposes`,
generic `calls`.

**Finding:** These are declared in `GRAPH_RELATIONS` and are used
**internally** by the graph derivation pipeline:

- `build_member` — used for workspace-aware path canonicalization in
  `sync.rs`.
- `includes_file` — emitted at `sync.rs:1026` for module inclusion
  tracking; used by `derive.rs` to resolve cross-file call targets.
- `reexports` — rename mapping at `sync.rs:116`; used by `derive.rs`
  for canonical name resolution in `test_reaches` and `calls_api`.
- `exposes` — used by `derive.rs` to determine public API surface for
  `rhai_callable_backing` resolution.
- `calls` — used by `derive.rs::test_reaches()` for transitive
  reachability computation; also consumed by `in_cycle()`.

**Recommendation: INTENTIONALLY SKIP.** These are query-only
infrastructure predicates in practice. They feed derivations (name
resolution, canonicalization, cycle detection, reachability) rather than
end-user lints. Making them into starter-pack rules would produce noise
(every function that calls another function would trigger a `calls`
rule) without actionable signal. Note the distinction from §2.5 below:
`build_member`/`includes_file`/`reexports`/`exposes`/`calls` are **not**
in `graph/audit.rs`'s `QUERY_ONLY_RELATIONS` const — nothing in the
engine would stop a project-authored rule from consuming them in an
audit finding — they're simply unused by any *starter* pack today, a
policy choice rather than an engine-enforced one. `hydrate.rs`'s
`needed_relations()` still means projects that don't author such a rule
pay zero hydration cost.

### 2.5 Rhai introspection predicates — intentionally skip

**Predicates:** `rhai_binding_diagnostic`, `rule_uses_predicate`,
`rhai_implements_predicate`, `rhai_callable_backing`,
`loads_rhai_script`.

**Finding:** These predicates feed **rule-system self-validation**:

- `rhai_binding_diagnostic` — emitted by `derive.rs` to flag Rhai
  predicate providers that reference predicates not declared in
  `SyntaxFacts::PREDICATES` or `GRAPH_RELATIONS`. This is a
  meta-rule: it validates the rule system itself, not the user's code.
  Unlike the §2.4 topology predicates, this one is structurally
  suppressed: it's in `graph/audit.rs`'s `QUERY_ONLY_RELATIONS` const
  (verified), so the engine itself won't turn it into an audit finding.
- `rhai_implements_predicate` — derived fact confirming that a Rhai
  provider script correctly implements a declared predicate.
- `rhai_callable_backing` — links a Rhai provider to the predicate it
  backs.
- `rule_uses_predicate` — links a rule to the predicates it references.
- `loads_rhai_script` — flags `engine.eval(<string literal>)` calls
  that load Rhai scripts at runtime (a hazard pattern, already
  covered by the `rhai` pack's `warn-rhai-eval-string-literal` rule).

**Recommendation: INTENTIONALLY SKIP** (except `loads_rhai_script`,
which is already wired). The `rhai_binding_diagnostic` family is
rule-system infrastructure. A starter-pack rule over
`rhai_binding_diagnostic` would be a meta-rule that only fires when
the project has custom Rhai predicate providers — a narrow audience.
The `rhai` pack already covers the user-facing hazard
(`loads_rhai_script` via `warn-rhai-eval-string-literal`). The
introspection predicates are correctly left as query-only
infrastructure for the `phr-mcp` predicate-provider tooling and
`wiki-drift` detection.

## Open questions

1. **`no_test_coverage` scope: all production functions or `pub` only?**
   The brief asks about public functions specifically. Flagging private
   helpers that are transitively tested through their callers' tests
   would be noise. But flagging private helpers that are NOT transitively
   tested is genuinely useful. Recommendation: flag all production
   functions in Phase 1, then assess false-positive rate from real
   usage and potentially restrict to `pub` in a follow-up.

2. **Should `warn-untested-public-function` be in the `rust` pack or a
   new `coverage` pack?** The `rust` pack is already large. A `coverage`
   pack would signal that test-coverage rules are opt-in. But users who
   select `--packs rust` expect comprehensive Rust rules. Recommend
   adding to `rust` pack initially; split if it becomes noisy.

3. **`test_reaches` vs `tested_by` for `no_test_coverage`: is transitive
   reachability too lenient?** A function that is only reached through a
   5-call-deep chain from a test may not be meaningfully tested. Consider
   a depth limit (e.g., `test_reaches` with max depth 3) in Phase 2.
   Requires reading the `test_reaches` implementation in `derive.rs`
   to determine if depth limiting is feasible.

4. **Should the config/IaC pack fixes (2.1) be bundled into one PR or
   separate?** The YAML ID-vs-action fix and the Lua `edited_file` join
   fix are independent. Separate PRs allow independent review and revert.
   But they are both trivial. Recommend one PR with two commits.

5. **Integration test strategy for config/IaC packs (1.6): should these
   use the same temp-project pattern as `syntax_integration.rs`?** The
   existing integration tests create a temp dir, write rules.json + a
   source file, run `pre-check`, and assert exit code + violation
   message. This pattern works for config/IaC packs but requires the
   graph to be hydrated (since the predicates come from graph
   extractors, not AST extractors). Verify that the integration test
   harness supports graph hydration or add it.
