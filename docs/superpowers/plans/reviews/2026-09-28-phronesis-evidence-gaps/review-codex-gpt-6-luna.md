# APPROVE WITH CHANGES

## Critical

- **Task C2 — redirect parsing can read a different file than the command wrote.** The proposed code takes the first handled result from `command_heads`, then calls `stdout_redirect_target` on it (PLAN-UNDER-REVIEW.md:988–995). But `command_heads` returns normalized **segments**, not just executable names, and splits on `|` (segment.rs:30–48). Thus `cargo test | tee run.log` becomes two segments; the handled `cargo test` segment has no redirect target, so the test output is missed. Conversely, the proposed C1 scanner sees `cargo test > /safe.log; cat /etc/secret` as one segment when called directly, and its whitespace tokenization does not parse shell quoting or operators safely. Parse the original segments while preserving redirection and pipeline relationships, and only follow a target attributable to the handled invocation. Add cases for pipelines, sequential commands, quoted/escaped targets, and multiple redirects.

- **Task C2 — allowed-root checks and the fixed cap do not make the read safe enough.** The plan canonicalizes then opens the target (PLAN-UNDER-REVIEW.md:997–1019), leaving a symlink/TOCTOU window; it also allows any file under the shared OS temp directory. The repo’s existing `security::read_file_capped` caps reads using the configurable `max_file_bytes()` and documents protection against FIFOs and unbounded files (security.rs:37–62, 261–274). Use a safe open strategy, require a regular file, constrain temp-file ownership/location more tightly, and reuse the capped reader with an explicit policy. Test a symlink that escapes the allowed root, a FIFO, and a target replaced between validation and open.

- **Task E1 — the regex does not reliably pair each Kani header with its own verdict.** The proposed `(?s)... .*?VERIFICATION` pattern (PLAN-UNDER-REVIEW.md:1383, 1398) can cross intervening harness headers when a header has no verdict, pairing it with a later harness’s verdict. The two-harness fixture only tests the case where both have verdicts (PLAN-UNDER-REVIEW.md:1406–1429). Parse bounded harness sections or make the pattern prohibit crossing the next header, then test missing verdicts, repeated output, and unrelated verification text. Also, the “real output” claim is not established by repository evidence; the fixture is synthetic.

## Major

- **Task A1 — the two-walk diff mislabels non-policy exclusions.** `discover_files` currently uses `WalkBuilder` with `.phronesisignore` and standard ignore behavior (run.rs:144–174). The proposed second walk disables only `.phronesisignore` (PLAN-UNDER-REVIEW.md:88–111), so files excluded by `.gitignore`, hidden-file defaults, or walker errors can also appear in `excluded`. The test only checks two `.phronesisignore` entries and does not cover overlaps with `.gitignore` or errors. Track which ignore source excludes each file, or otherwise ensure the reported set is exclusively `.phronesisignore` policy; add overlapping-ignore and hidden-file tests. The suggested `Option::is_none_or` also needs an MSRV 1.90 check before adoption.

- **Task A2 — exclusion is not equivalent to “lexical rules only.”** `rule_has_ast_predicate` exists and is `pub(super)` (engine.rs:95–99), but the proposed filtering classifies any rule containing an AST predicate as structural (PLAN-UNDER-REVIEW.md:204–207). Mixed AST plus `new_content_contains` rules would still run their lexical condition on excluded files. Define mixed-rule semantics and test them. Also, the suggested report path collection is not sorted explicitly (PLAN-UNDER-REVIEW.md:247–251); discovery ordering is not a documented API guarantee. Sort report paths and clarify `files_scanned` semantics because the plan counts excluded files as scanned while existing output means files offered to the scan (run.rs:31–43).

- **Task A3 — the test does not prove the exemptions work.** The test checks that markers exist in the file (PLAN-UNDER-REVIEW.md:382–405), but `file_exempts_rule` only reads leading `//!` lines and only suppresses rules with `doc_excepted` (engine.rs:256 onward; 446). Of the three named rules, `audit-newtype-id-string` and `audit-allow-dead-code-in-src` set `doc_excepted`; `audit-string-concat-with-plus` does not (rules_rust.rs:174–184, 280–301). A marker alone cannot exempt that lexical rule. Add `doc_excepted` or choose another targeted mechanism, and test actual audit results against self-triggering content. The proposed test also says “self-reference … per rule” but never runs the audit.

- **Task B1 — command directory extraction is too permissive and incomplete.** The proposed `git -C` regex matches anywhere, including quoted text or a comment, and takes only the first matching `-C` (PLAN-UNDER-REVIEW.md:553–594). Its `cd` path parser does not handle escaped spaces, environment expansion, or `cd` followed by a newline; it also can accept `&&` inside later text as evidence that the initial `cd` hands off. The quoted-path tests do not include embedded quotes/escapes or command substitutions. Given shell syntax is not parsed here, prefer a conservative parser that returns `None` for ambiguous forms and test comment/string, wrapper, multiple `-C`, and `cd` without a real separator.

- **Task B2 — relative `cd` paths are resolved against the wrong working directory.** `probe_root_for` joins relative paths to `project_root` (PLAN-UNDER-REVIEW.md:677–698), but a shell tool’s starting cwd may differ from the project root. Its test uses only an absolute worktree path. Either capture the shell’s effective cwd as input or restrict accepted paths to absolute paths, and test relative paths from a different cwd. The design also adds a `repo_dir` event extra while Task B3 assumes the unit report can decode it; current `CommitRow` has only `sha` and `band` (unit_report.rs:24–29), so update every output representation and verify the JSON contract.

- **Task C3 — `ingest` can journal misleading or phantom evidence.** `record_from_output` is described as returning `(subject, tags)` and appending a record per tag set, but the implementation appends even when parsing produces no outcome tags (PLAN-UNDER-REVIEW.md:1117–1159). It also unconditionally adds `outcome:output_from_file` although the CLI itself reads a saved file; that tag is ambiguous between adapter redirect recovery and explicit ingestion. Define behavior for unrecognized/no-result output, distinguish explicit ingest provenance, and test nonzero exits, empty output, unknown toolchain, and proof outcomes. `SignalError` currently has only `NotEnabled`, `UnknownSignal`, `Subject`, and `Journal` (outcomes/mod.rs:66–77); `UnknownSignal` is the wrong error for an unhandled command.

- **Task E2 — dropping unmapped proof facts can leave stale passes active.** Existing proof parsing emits a `proof_run_outcome` when no result matches, specifically to prevent stale prior passes surviving (toolchain.rs:375–407). The proposed transform drops unbound `proof_outcome` facts but preserves the run-level fact (PLAN-UNDER-REVIEW.md:1561–1589). That may be correct only if the run-level fact reliably retracts every prior property pass; the test does not check journey/confidence state across an earlier pass followed by an unbound or failed run. Add stateful journal tests. Also, `load_properties(...).unwrap_or_default()` silently treats malformed property data as no bindings; report the load error and avoid emitting misleading “unbound” messages.

- **Task E3 — planned end-to-end test cannot produce a current `proof` confidence signal as described.** The plan asks `confidence --json` to show `proof` after `phr-mcp signal ingest` (PLAN-UNDER-REVIEW.md:1622–1633). The C3 proposal routes through `extract_from`, but current `outcomes::report` and `ConfidenceReport` describe compile/tests/bug signals (outcomes/mod.rs:34–58), and proof tags’ integration with confidence must be verified before promising that result. Add an explicit confidence derivation test and adjust the plan’s claim if proof remains journal-only. The encoding itself belongs in the tracked `.phronesis/properties.json`; unlike `.phronesis/toolchains.json`, it is tracked here (`git ls-files` confirms both). The coordination note at line 1608 therefore needs resolving before this part can ship.

- **Task D1 — tracked seeding can overwrite a worker’s independent edits and hide future changes.** The proposed `--seed-tracked` copies over a tracked worktree file then sets `skip-worktree`, with the return from `git update-index` ignored (PLAN-UNDER-REVIEW.md:1324–1342). It does so whenever bytes differ, without proving the difference is only source-side uncommitted state or checking whether the worker already changed the file. Add a three-way comparison against HEAD, refuse conflicts, check and report `update-index` failure, and provide a deliberate way to clear `skip-worktree`. The test verifies only a clean worker branch and never exercises conflict or cleanup behavior. Part D remains a design-only review because its repository is outside this checkout.

## Minor

- **Task A4 — docs overstate marker coverage.** The proposed wording says a `//! phronesis-allow` marker can silence a structural rule (PLAN-UNDER-REVIEW.md:472–481), but `file_exempts_rule` is called for all rules only when `doc_excepted` is set (engine.rs:446). Scope the claim to rules that opt in and clarify marker placement.
- **Task C1 — tested redirect forms are narrower than the implementation claims.** `split_whitespace` cannot preserve a quoted path with spaces when it appears as an attached target (`>out dir/log`), and `tee` parsing skips every option-looking token, including a legitimate filename beginning with `-` (PLAN-UNDER-REVIEW.md:851–897). Use tokenization that understands quotes and add those cases.
- **Task E1 — project registration test has the wrong deserialization assumption.** `.phronesis/toolchains.json` begins with `_doc` (toolchains.json:1–4), while `ToolchainDef` uses strict deserialization; the plan notices this only parenthetically (PLAN-UNDER-REVIEW.md:1432–1443). Load through `toolchain::registry` or explicitly deserialize the documented file format. The test should also assert the registered definition’s source and matching behavior.
- **Global constraints — CI command and MSRV are real, but the plan omits a few compatibility checks.** CI runs fmt, clippy with all targets and `-D warnings`, workspace tests, and `phr-mcp audit --fail-on block` on Rust 1.90 (.github/workflows/ci.yml:12–29); workspace edition is 2024 and MSRV 1.90 (Cargo.toml:7–8). The plan’s global gate matches CI. Before relying on newer convenience APIs, check them against MSRV; avoid broad `unwrap_or_default` on data-load errors. The code snippets’ dense one-line expressions should be rustfmt’d before clippy review.
