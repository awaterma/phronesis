## Major

- **F1, F2 — lcov hits must require an executed body line.** The plan currently counts any positive `DA` line in the full function span, including the definition line (F2, `PLAN-UNDER-REVIEW.md:2119`, `2281`). That over-attributes coverage.py data: executing an import can mark a `def` line as covered without executing the function body. The plan’s own fixture has exactly this shape for `save`: `DA:4,1` on the definition, followed by `DA:5,0` on the body, yet expects no `save` hit (`PLAN-UNDER-REVIEW.md:2151-2168`). Define the hit rule using positive DA counts on executable body lines only; exclude the function header/decorator lines, and add import-only and multiline-header cases.

- **F1 — Python’s test-file filter misses some paths classified as tests by the graph.** The proposed collector excludes Python files based on `classify_python_file` and `conftest.py`, but omits the explicit `tests/` exclusion in the task’s own expected cases (`PLAN-UNDER-REVIEW.md:1988-2001`, `2085-2093`). The graph classifier considers files under `tests/` test files, as well as `test_*.py` and `*_test.py` (`graph/python.rs:18-32`). Reuse that classifier and add the missing `tests/` case to the proposed test. `conftest.py` is deliberately classified as production, so its separate exclusion should remain explicit.

- **F2 — Keep lcov’s record kinds compatible with the store.** The plan proposes `hit_kind: "function"` (`PLAN-UNDER-REVIEW.md:2119`, `2284-2289`), but `validate_record` only accepts `"region"` or `"branch"` and requires their respective ID prefixes (`store.rs:440-475`). Existing function hits use `kind: "hit"` and `hit_kind: "region"`; branch hits use `"branch"` (`collect.rs:158-168`, `186-196`). Use `"region"` for Python function hits, and test a successful import through the real CLI/store path. The store is `.phronesis/coverage.jsonl` plus `.phronesis/coverage.index` (`store.rs:110-113`); the proposed test’s fallback path obscures that contract (`PLAN-UNDER-REVIEW.md:2163-2165`).

- **F2 — Do not silently accept an lcov file with no `SF:` records.** `import_export` currently rejects empty record sets through single-revision/tool validation before writing (`import.rs:70-93`). The proposed directory importer can return zero records if paths fail to relativize or are filtered, while still counting tests (`PLAN-UNDER-REVIEW.md:2258-2293`). Ensure empty or wholly unjoinable imports fail clearly and leave the existing store untouched; retain all-or-nothing semantics.

- **F2 — Make container path mapping deterministic and collision-safe.** The proposed `relativize` returns the first existing suffix, not the longest (`PLAN-UNDER-REVIEW.md:2234-2253`), despite the decision promising the longest existing suffix (`PLAN-UNDER-REVIEW.md:1933`). If both `pkg/x.py` and `app/pkg/x.py` exist, that can bind container coverage to the wrong source. Search suffixes from shortest-to-longest (or select the longest matching relative path) and reject ambiguity rather than guessing.

- **F3 — Construct graph test IDs with the graph’s actual module shape.** The plan describes `python:<ns>::<module>::<test_fn>` and proposes IDs such as `python:pkg::tests.test_store::test_load` (`PLAN-UNDER-REVIEW.md:1933`, `2153-2154`). The graph builds module paths by joining every path segment with `::`, then appends the test name (`graph/python.rs:41-58`, `144-164`); a concrete test ID is `python:pyside::tests::test_utils::test_load` (`graph/python.rs:543-550`). Do not invent dot-separated module names or omit the unit namespace. Use a shared qualification helper, with a test asserting the complete exact ID.

- **F3 — Handle parametrized pytest node IDs and shell quoting.** The proposed collector parses node IDs, then places them into shell commands and filenames (`PLAN-UNDER-REVIEW.md:2318-2339`). Pytest node IDs can include parameter suffixes, and arbitrary IDs/file paths may contain characters meaningful to a POSIX shell. Preserve the complete node ID for pytest selection, quote it safely, and encode the graph ID for filenames instead of using raw IDs as output paths. Add parametrized and metacharacter cases. The per-test `coverage run` invocation is the right isolation model if each run starts with a fresh data file.

- **F3 — Add a Python rendering path to selection, not just a display change.** Current `select` joins changed regions to stored hits and graph edges; its human table prints the test ID as stored (`select.rs:206-229`, `375-473`). The plan says “render” Python IDs as commands (`PLAN-UNDER-REVIEW.md:2314`, `2319`), but does not identify a command output surface or specify graph lookup in the selection data path. Define where the runnable command appears and ensure the `defines_test` edge supplies the source file; include a test proving a `python:` ID is recognized and rendered.

## Minor

- **F1 — Factor ordinal assignment before reusing it.** Rust function ordinals are currently assigned inside `function_sites_by_node` (`region_map.rs:432-458`); the `extract_sites` function at `479-517` assigns ordinals to branch anchors, not function paths. The proposed `assign_ordinals` helper is not present yet. Factor the Rust function-path ordinal logic into a shared step and test duplicate Python definitions and nested definitions against Rust behavior.

- **F1 — Confirm inclusive line ends.** Tree-sitter node positions are zero-based rows; the current Rust code converts `end_position().row` directly to a one-based `end_line` (`region_map.rs:449-455`). If a Python function ends with a newline, `end_position()` can be on the next row at column zero, so that conversion may include the following line. Probe a real Python parse and define an inclusive end calculation that accounts for end column. `tree-sitter-python` is pinned at 0.25.0 (`crates/phronesis-mcp/Cargo.toml:60`, `Cargo.lock:2174-2175`). `parse_python` uses that grammar (`syntax/parsed.rs:51-60`); the repository does not currently test whether `async def` appears as `function_definition`. Add an async extraction test rather than assuming it.

- **F2 — Import revision stamping does not prove container source identity.** The host can stamp its HEAD revision, but when coverage ran in a devcontainer, the measured source may differ from the host’s tracked checkout even if the host tree is clean. The current collector explicitly guards tracked dirty paths because it reads source and runs tests against that same working tree (`collect.rs:297-342`). Add a container-side revision/source fingerprint to the exported evidence and verify it at import, or state the weaker guarantee and reject claims that the host stamp alone proves source identity.

- **F3 — Preserve pytest’s graph classification conventions.** The classifier recognizes `test_*.py`, `*_test.py`, and `tests/` paths (`graph/python.rs:18-32`), while graph test names are emitted only for functions whose names begin `test_` (`graph/python.rs:158-168`). Ensure collection handles class-qualified methods consistently and clearly reports pytest-collected tests the graph does not identify.

- **F4 — Route the actual hook hydration path through language-aware mapping.** Changed-region facts are computed in coverage hydration by `changed_regions` (`coverage/hydrate.rs:163-185`), which calls the region map. The property hydration path also calls `coverage::region_map::changed_regions` (`properties/hydrate.rs:68-80`). The plan’s F4 search target emphasizes `hook/edit_images.rs` and coverage hydration but may miss property hydration. Update the shared region-map dispatch and test both hook and property consumers where applicable.

- **F5 — Don’t claim Python CI coverage without adding a Python job or fixture.** Current GitHub workflows show Rust tests and a Python helper script, but no Python setup/test step (`.github/workflows` search: `cargo test` and `python3 scripts/verify-crates-io.py`). The BDD coverage feature contains Rust coverage scenarios and no Python scenario (`tests/features/coverage-evidence.feature:1-23`). Add a focused Python lcov fixture/scenario and CI coverage of the parser/import path, or explicitly document that Python itself is not run in CI.
