# Inventory: packaged `new_content_contains` uses

Companion to `SPEC-structural-rule-migration.md` §"Freeze the inventory"
(implementation plan step 1). Generated by reading every `fn *_rules() -> Value`
starter-pack definition in `crates/phronesis-mcp/src/init.rs` and classifying
each `new_content_contains` condition against the spec's three categories:
**structural** (program shape — belongs behind a parser-backed fact),
**command-scoped lexical** (Bash command intent — belongs behind
`bash_command_matches`), or **textual** (prose or an unsupported
language/construct — stays lexical by design).

Scope: this table lists every `new_content_contains` condition that appears in
a packaged starter rule (a `fn *_rules()` function reachable from a pack
selection in `init.rs`). It excludes:

- generic engine/lexical-predicate tests that exercise `new_content_contains`
  itself as a mechanism, not a policy — e.g.
  `crates/phronesis-mcp/tests/hook_integration.rs`,
  `crates/phronesis-mcp/tests/save_rules_integration.rs`,
  `crates/phronesis-mcp/tests/bdd.rs`, and the BDD feature files under
  `crates/phronesis-mcp/tests/features/`;
- documentation and ADR pages that merely *name* the predicate
  (`AGENTS.md`, `CLAUDE.md`, `CHANGELOG.md`, `docs/specs/*`,
  `.phronesis/wiki/decisions/*`) rather than define a shipped rule;
- the `init_integration.rs` tests that assert a generated rule's *id* is
  present — those are covered indirectly by the packaged rule they exercise.

The table freezes the 35-rule lexical baseline and is updated in place as rows
migrate or retire. A completed row therefore remains as migration history even
when its former rule ID is no longer present in `init.rs`. Where one rule
carries multiple `new_content_contains` clauses joined by `or`, the row notes
the clause count.

Note on quoting below: the five LLM deflection phrases are rendered with a
zero-width space inserted mid-phrase so this document itself does not trip
the very deflection rules it is cataloguing when it is written to disk. The
inserted character is not part of the matched pattern; see the rule's actual
`when` clause in `init.rs` for the exact literal.

## Legend

- **Tier**: A = existing producer can likely be reused (needs equivalence
  fixtures before cutover); B = evaluation-queue candidate for a new
  parser-backed fact; C = intentionally lexical (spec §"Tier C").
- **Disposition**: planned or completed treatment. Completed rows remain here
  so the frozen baseline continues to account for every migrated clause.

## Totals

- Baseline: 35 packaged rule IDs used `new_content_contains` (45 individual
  clauses, since two Swift rules each pack multiple clauses behind `or`).
- Current after completed migrations and retirements: 9 packaged rule IDs
  use `new_content_contains` (9 clauses). Completed rows remain above as
  migration history.
- Textual (Tier C, stays lexical, no annotation needed): 5 (`llm` prose
  deflection rules).
- Command-scoped lexical (Tier C, migrated to `bash_command_matches`): 1
  (`nudge-verify-before-commit`; no longer counted in the current total).
- Rhai source (Tier C, stays lexical pending a Rhai parser): 1.
- Structural, Tier A completed: 1 (`warn-any-in-src`, retired in favor of the
  canonical structural rule).
- Structural, Tier B completed or retired: 25.
- Structural, narrow/anomalous — not a portable language construct, flagged
  as a pre-existing pack-scope defect outside this migration's tiers: 2
  (`block-await-on-sync-execute-all-agenda-items`,
  `block-await-on-sync-fire-all-consequences`).

No rule in this inventory is a language AST claim by itself — none of the
current conditions call a tree-sitter node kind; they are all regex substring
matches over the diff/edit payload. This document does not claim otherwise:
only the *proposed* replacements in the "Proposed/existing predicate" column
are structural facts.

## Stable rule IDs

Rule IDs remain stable when a condition is replaced in place. Tier A is the
documented exception: `warn-any-in-src` duplicated the already-shipped
`warn-ts-explicit-any-ast` structural rule, so keeping both IDs would preserve
duplicate consequences rather than policy compatibility. The structural ID is
canonical and the lexical ID is retired. Later migrations must keep their IDs
unless an equally concrete collision is documented.
