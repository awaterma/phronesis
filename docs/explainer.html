Phronesis &
the rules
that do not fade.

Notes on a small RETE rules engine, the MCP server that hosts it, and the hook surfaces we use to keep project guidance alive across a long working session.

Andrew Waterman with Claude · Anthropic 2026

※

On the name — phronesis, practical wisdom.

Phronesis (φρόνησις) is Aristotle's term for practical wisdom — the deliberative virtue of knowing what to do here, now, in this particular case, and under genuine uncertainty. It is not the same as theoretical knowledge or technical skill; it is the cultivated judgment that an experienced practitioner brings to a concrete situation, where the general principle does not quite reach and the right action has to be worked out from particulars.

We have found this an apt name for the work this project is asked to do. A rule that says "don't use .unwrap() in src/" is not a theorem and does not pretend to be one. It is a situated judgment: in this codebase, under these constraints, given everything we have learned the hard way, do this rather than that. What this engine persists across compression boundaries is precisely that kind of small, hard-won, project-specific maxim — the practical wisdom of a particular team about a particular system, rendered durable across sessions in which context windows fill, conversations get summarized, and the guidance the operator most needs may be the guidance most likely to have faded.

Marginalia. The crate is phr. The binary is phr-mcp. The on-disk directory is .phronesis/. The MCP server name is phronesis. We kept the long name in user-facing places and the short name everywhere a developer actually types.
§01
1

The premise — guidance fades, work continues.

Anthropic's Claude Code, Google's Gemini CLI, and the broader family of LLM-assisted development environments share a common pattern at startup: they load whatever project-level guidance they find — a CLAUDE.md, an AGENTS.md, a system primer — at session initialization, and place it in the model's context window. As the session continues, that window fills with code, command output, and conversation. Older content is summarized by auto-compaction steps; even content that literally remains in context receives less attention from the model as new material accumulates between it and the current prompt. The directive we most need at hour three may have last been read carefully in token eight hundred.

This is not a bug; context windows are finite, and compaction is the price of long-running sessions. It does, however, mean that any project convention encoded only in prose — any instruction that lives solely in the loaded markdown — has a practical half-life. The deflective phrasing we warned the model against in turn one tends to come back in turn ninety. The rule about workspace flags that we established on Monday is no longer reliably retrieved from context on Thursday afternoon. The shape of the project — the set of small, hard-won particulars one is meant to honor — slowly fades, whether through explicit summarization or through the gentler erosion of attention.

Phronesis came out of an attempt to address this directly, by moving enforcement out of the conversation entirely. Rules live on disk in .phronesis/rules.json; they are re-read by lightweight hooks at every relevant tool call; they fire from outside the context window. They cannot be compressed away, because they were never loaded into context to begin with. They fire the same in token nine hundred thousand as they do in token eight hundred.

Marginalia, i. Conversation-resident guidance has a half-life proportional to token-budget pressure. Disk-resident rules have none. We have found that this asymmetry — and not any cleverness about the rule language itself — is what the project is really about.

2

What it is — a small engine, hosted as a hook.

Phronesis is a RETE rules engine. RETE was developed by Charles Forgy in the late 1970s at Carnegie Mellon and published in its canonical form in the 1982 paper Rete: A Fast Algorithm for the Many Pattern / Many Object Pattern Match Problem. It has lived inside production-rule systems ever since — inside expert systems, business-rules platforms, event correlation engines, the JBoss Drools framework one of the authors used in earlier participatory-modeling work, and any number of others. The algorithm itself is straightforward: facts enter a network, conditions match against them in a compiled discrimination graph, and consequences fire when all of a rule's conditions are satisfied. There is nothing especially novel in our use of the algorithm; what is new here is the purpose to which we have put it. We use RETE to lint LLM tool calls.

Phr-MCP is the wrapper around the engine: a single Rust binary that exposes it three ways. It runs as an MCP server over stdio, for any MCP-capable client. It runs as a set of CLI subcommands that bind directly to the Claude Code and Gemini CLI hook protocols. And it runs as a whole-tree audit tool. The hooks are where the durability property comes from. They are invoked by the host (Claude Code, Gemini CLI) at well-defined moments — before a tool fires, after it applies, when a session opens, when the user submits a prompt — and they re-read the rules file from disk on every invocation.

That last property is the structural point. The hook does not cache anything between invocations. It does not depend on the model's memory or on any state retained in the conversation. It opens a file, parses it, runs the network against the facts extracted from the current tool call, prints a result, and exits. Whatever the model has forgotten, the hook still has access to — because the hook never knew anything to begin with, and reads the rules fresh from disk every time it is asked to fire.

Marginalia, ii. The engine itself is unremarkable; RETE is a textbook algorithm and there is no shortage of implementations. What we have found valuable is the location of the engine: outside the conversation, invoked by the conversation's host. That, more than anything else about the engine, is the substantive move.

We have kept the picture deliberately small. There is no daemon, no socket, no shared state between invocations of any kind. Every hook fire is a fresh process that reads the rules from disk, evaluates them against the current tool call's facts, and exits. The persistence we care about comes from the file system, not from anything the engine itself is asked to remember.

A rule is a small refusal the project keeps making, even after it has forgotten the conversation in which it was first imagined.

3

Anatomy of a rule — JSON, conditions, consequence.

Rules are JSON. We considered, at one point, introducing a small domain-specific language for rule authoring — Drools DRL did this years ago and the expressivity is genuinely attractive — but in the end we decided against it. Anyone using phronesis is already writing in some other language (Rust, Python, TypeScript, Swift); asking them to learn a rules DSL on top of that seemed to us like the kind of overhead that quietly kills adoption. A rule is therefore just a JSON object with five fields: an identifier, a phase, an integer priority, an array of conditions, and an array of actions. Conditions are predicates with arguments; the predicates are evaluated against facts extracted from the tool call. When all conditions for a rule match, the rule fires — meaning its actions run.

In practice, only two action types matter: constraint_violation (which blocks the call at pre-phase and warns at post-phase) and constraint_warning (which always warns). The first parameter of either is the human-readable message printed to the user when the rule fires. This same message is also what the model sees, both during the session-start summary and in the hook's stderr output, which is part of how a rule's authored intent gets communicated back to the model that triggered it.

Marginalia, iii. Predicates are a small fixed vocabulary — content matches, file extension gates, AST shapes derived through tree-sitter, Bash command analysis. Adding a new predicate requires Rust code. Writing new rules that use existing predicates does not.
predicate
A named fact-matcher provided by the host. Examples: new_content_contains (substring match against the diff), file_extension_is (gate), function_returns_result_string (AST), function_param_count_high (AST), cargo_command_lacks_workspace (Bash content), file_line_count_above (audit-only gate).
fact
A tuple produced from the tool call payload: the file path, the added text, the removed text, the AST-derived shapes, the Bash command string. Facts are inserted into the RETE network; conditions unify against them.
phase
When a rule runs. pre rules block (exit 2); post rules warn (exit 1); audit rules are silent at hook time and only fire during phr-mcp audit.
§04
4

Three surfaces — enforce, sweep, re-inject.

The same rule format serves three distinct moments in the development cycle, each with a different cadence, a different audience, and a different mode of action. Taken together, they cover the life of a piece of project guidance: from moment-of-action enforcement at the hook, to periodic debt review across the whole tree, to session-wide prose steering through the durable directive file. We have found that no single surface is adequate on its own, and that the three of them in combination address the gap that motivated the project.

Marginalia, iv. Hook rules catch what one has just written. Audit rules catch what is still there. Durable directives shape what is about to be written.

Hook-time

block · warn · allow

Pre-check rules fire before an Edit, Write, or Bash call applies its changes. A failing condition exits 2, which the host honors by refusing the call. Post-check rules fire after the edit has been applied; they exit 1 to warn but cannot reverse what has already been done to the tree.

  • phase: pre — blocks the call
  • phase: post — warns on the call
  • fires once per tool invocation

Audit

debt · sweep · trend

A whole-tree scan against every rule tagged audit: true, producing per-rule hit counts with file and line locations. Each audit run also appends a snapshot to the action log, so that phr-mcp trend can report whether the pile is shrinking from one week to the next.

  • phase: audit — never at hook time
  • opt-in via audit: true
  • writes a trend snapshot per run

Durable directives

prose · re-inject

A small markdown file at .phronesis/durable.md. Its contents are re-injected into the model's context at every SessionStart and every UserPromptSubmit. CLAUDE.md fades; this does not. Reserved for the few directives that absolutely must survive context compression.

  • injected by session-context
  • injected by turn-context
  • prose, not enforced — re-read every turn

How it slots in — one binary, one rules file.

phr-mcp init writes a small set of files into a project to wire phronesis into its host environment. Hook configuration goes into the respective settings files for each host (.claude/settings.local.json for Claude Code; .gemini/settings.json for Gemini CLI, which also carries Gemini's MCP server registration in the same file). A separate .mcp.json registers the server for Claude Code and any other MCP-capable client. The starter rules pack lives at .phronesis/rules.json, and an entry is appended to .gitignore so phronesis's log and backup files are not accidentally committed. We have taken care to make re-running idempotent: existing configuration is preserved, and only the entries owned by phronesis are added or refreshed, so init can be re-run safely against an established project without fear of clobbering other tooling already present.

Marginalia, v. The init command is the only operation in the entire tool that writes files outside the .phronesis/ directory itself. Everything else — the hook, the audit, the trend report, the drift check — is read-only as far as the project tree is concerned.
.claude/settings.local.json

Claude Code hooks

PreToolUse and PostToolUse entries point at phr-mcp pre-check and post-check. SessionStart and UserPromptSubmit entries handle context injection.

.gemini/settings.json

Gemini CLI hooks

BeforeTool and AfterTool entries provide the equivalent pre/post enforcement. BeforeModelRequest is Gemini's name for the per-turn context injection point.

.mcp.json

MCP server registration

Exposes mcp__phronesis__* tools — assert facts, fire rules, audit the codebase, query the trend — to any MCP-capable client over stdio.

.phronesis/rules.json

The rules pack

A JSON array. Composable starter packs ship with the binary: llm for behavior, rust for code shape, plus python, typescript, swift. Edit in place; rules are re-read from disk on every hook. 

# a typical bootstrap
$ cargo install --path .
$ phr-mcp install              # user-scope MCP registration
$ cd ~/Git/my-project
$ phr-mcp init --packs llm,rust # project-scope wiring + starter rules
$ phr-mcp audit                # sweep existing debt
$ phr-mcp trend                # debt over time
$ phr-mcp claude-md-drift      # which CLAUDE.md bullets lack rules
§06
6

A closing note — on what rules cannot do.

We want to be clear about what phronesis does and does not claim to do. It persists the prompt-to-think; it does not persist the thinking. A rule that warns trace the call chain end-to-end before claiming done will fire reliably on every git commit -m, and the model (or the human at the keyboard) will see that warning. But whether the operator actually traces the chain in response remains the operator's choice. The rule cannot make anyone do the work; it can only ensure that the question is asked again, even after the conversation in which it was first imagined has long since been compressed away.

What the project earns by moving enforcement out to disk is durability — a known, fixed set of refusals and reminders that fires the same on hour one and hour ten, in token eight hundred and in token nine hundred thousand. This is a different thing from cleverness, and a much smaller claim than it is now fashionable to make about software of this kind. In our experience, however, it is a useful one. The small project-specific maxims that we would otherwise have to repeat across sessions are simply there, on disk, doing their work whether or not the conversation has remembered them.

Marginalia, vi. We think of rules as durable scaffolding for habits, not as a substitute for them. They catch shape, not behavior; the rest is still ours to do.
The rule fires the same in token nine hundred thousand as in token eight hundred.
